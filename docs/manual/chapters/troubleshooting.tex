This chapter collects the problems that users most often run into, grouped by
symptom, together with their causes and solutions. If a problem is not
covered here, run the failing code with warnings enabled
(\code{python -W default ...}), check the installation with the commands of
Section~\ref{sec:install-verify}, and report the issue with the full error
message and the output of \code{pip list} at
\url{https://github.com/EricDMW/My_Tool_Box/issues}.

\section{Rendering on machines without a display}\label{sec:trouble-headless}

\paragraph{Symptom.} Rendering fails or hangs on a compute cluster, in a
container, over SSH or in continuous integration, often with messages such as
\code{cannot connect to X server}, \code{no display name} or
\code{TclError}.

\paragraph{Solution.} Use \code{render\_mode="rgb\_array"}, which draws
off-screen and never needs a display: the matplotlib renderers draw on an Agg
canvas that is independent of the active matplotlib backend, and the
Pistonball renderer draws on pygame surfaces without initialising the display.
In addition, select non-interactive back ends for any other plotting code:

\begin{shellcode}
export MPLBACKEND=Agg            # matplotlib: off-screen rendering
export SDL_VIDEODRIVER=dummy     # pygame: no window system
python train.py
\end{shellcode}

The same settings can be made at the top of a script, before matplotlib or
pygame is imported:

\begin{pycode}
import os

os.environ.setdefault("MPLBACKEND", "Agg")
os.environ.setdefault("SDL_VIDEODRIVER", "dummy")
\end{pycode}

Frames returned by \code{env.render()} can then be recorded to GIF or MP4
(Section~\ref{sec:examples-recording}) and inspected later. The test suite,
the benchmark script and the CI workflow use exactly these settings.

\section{No window appears in human mode}\label{sec:trouble-human}

\paragraph{Symptom.} With \code{render\_mode="human"} nothing is shown, and
a \code{RuntimeWarning} states that the active matplotlib backend is
non-interactive.

\paragraph{Cause.} \code{"human"} mode opens a window through matplotlib,
which needs an interactive backend such as TkAgg or QtAgg and a display.
When matplotlib falls back to Agg (because no GUI toolkit is installed, no
display is available, or \code{MPLBACKEND=Agg} is set), the environment warns
once and renders nothing. Pistonball's window is opened by pygame and needs a
display, but no matplotlib backend.

\paragraph{Solution.} Check which backend is active:

\begin{shellcode}
python -c "import matplotlib; print(matplotlib.get_backend())"
\end{shellcode}

If it prints \code{agg} (any case), install a GUI toolkit and select it:

\begin{itemize}
  \item TkAgg needs Tk: \code{sudo apt-get install python3-tk} (Debian,
    Ubuntu), \code{sudo dnf install python3-tkinter} (Fedora),
    \code{brew install python-tk} (Homebrew) or \code{conda install tk}.
  \item QtAgg needs a Qt binding: \code{pip install PyQt6} (or \code{PySide6}).
\end{itemize}

Then unset \code{MPLBACKEND} or set it explicitly, for example
\code{export MPLBACKEND=TkAgg}. In a Jupyter notebook, \code{"human"} mode is
not the right tool: render with \code{"rgb\_array"} and display the frames
with \code{matplotlib.pyplot.imshow} or save an animation. Over SSH, either
enable X forwarding (\code{ssh -X}) or record the episode and copy the file.

\section{``Out of date'' warnings for -v0 environment ids}\label{sec:trouble-outofdate}

\paragraph{Symptom.} Creating \envid{WirelessComm-v0} or
\envid{KuramotoOscillator-v0} with \code{gymnasium.make} prints

\begin{textcode}
DeprecationWarning: WARN: The environment WirelessComm-v0 is out of date.
You should consider upgrading to version `v1`.
\end{textcode}

\paragraph{Cause and solution.} Gymnasium assumes that a higher version
suffix is a newer revision of the same environment. In \pkg{env\_lib} the
suffixes denote preset configurations: \envid{WirelessComm-v1} is the
$4 \times 4$ grid, not an improved \envid{WirelessComm-v0}. The warning is
harmless and can be ignored. \code{env\_lib.make}, which otherwise behaves
like \code{gymnasium.make}, suppresses it. To silence it when calling
\code{gymnasium.make} directly:

\begin{pycode}
import warnings
import gymnasium as gym
import env_lib  # registers the ids

warnings.filterwarnings("ignore", message=r".*is out of date",
                        category=DeprecationWarning)
env = gym.make("WirelessComm-v0")
\end{pycode}

\section{AJLATT deprecation warnings}\label{sec:trouble-ajlatt}

\paragraph{Symptom.} Creating an AJLATT environment prints warnings such as
\code{AJLATT parameter 'num\_Robot' is deprecated; use 'num\_robots'} or
\code{parameter 'figID' no longer has any effect and is ignored}.

\paragraph{Cause.} The environment is configured by the \code{AJLATTConfig}
dataclass since version 1.0. The legacy keyword names of the former
\pkg{argparse}-based configuration are still accepted by
\code{AJLATTEnv(...)}, \code{env\_lib.ajlatt\_env(...)},
\code{env\_lib.ajlatt\_env.make(...)} and \code{AJLATTConfig.from\_kwargs},
but translated with a \code{DeprecationWarning}.

\paragraph{Solution.} Rename the arguments as in
Table~\ref{tab:trouble-ajlatt}; Appendix~\ref{app:migration} shows complete
before-and-after examples.

run \code{python -W default::DeprecationWarning script.py} to see every
translation when migrating a code base.

\section{PyTorch, GPUs and devices}\label{sec:trouble-torch}

\paragraph{Installing a CPU or a CUDA build.}
The \code{torch} extra installs the default PyTorch wheel of the platform,
which on Linux is a large CUDA build. For CPU-only machines install the CPU
wheel first (\code{pip install torch -{}-index-url
https://download.pytorch.org/whl/cpu}); for a specific CUDA version use the
command shown at \url{https://pytorch.org/get-started/}. Check the result
with

\begin{shellcode}
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
\end{shellcode}

\paragraph{The Kuramoto PyTorch backend.}
\code{KuramotoOscillatorEnvTorch} accepts \code{device="cpu"},
\code{"cuda"}, \code{"cuda:<index>"}, a \code{torch.device}, or
\code{"auto"}, which selects the first GPU when CUDA is available and the CPU
otherwise (the registered id \envid{KuramotoOscillatorTorch-v2} uses
\code{"auto"}). Requesting \code{"cuda"} on a machine without CUDA raises a
\code{ValueError} that suggests \code{"auto"} or \code{"cpu"}. Observations
returned by \code{reset} and \code{step} are always NumPy arrays; the batched
accessors \code{get\_batch\_observations()} and \code{get\_batch\_rewards()}
return tensors on the environment's device. A GPU pays off for large batches
of systems; for a single small system the CPU is faster because of the
transfer and launch overhead.

\paragraph{neural\_toolkit devices.}
The networks take a \code{device} argument (default \code{"cpu"}) that is
passed to \code{Module.to}; \code{"auto"} is not accepted there. Choose the
device explicitly and move the inputs to it:

\begin{pycode}
import torch
from toolkit.neural_toolkit import MLPPolicyNetwork

device = "cuda" if torch.cuda.is_available() else "cpu"
policy = MLPPolicyNetwork(8, 4, device=device)
logits = policy(torch.randn(32, 8, device=device))
\end{pycode}

\code{NetworkUtils.load\_checkpoint} loads tensors onto the device of the
model by default, so checkpoints written on a GPU load on a CPU-only machine.
Checkpoints written before version 1.0 cannot be loaded
(Section~\ref{sec:neural-changes}).

\section{Video export}\label{sec:trouble-video}

\paragraph{Symptom.} Saving a \code{.mp4} (or \code{.webm}, \code{.avi},
\code{.mov}, \code{.mkv}) file fails with \code{Video export requires imageio
and imageio-ffmpeg}, or \pkg{imageio} reports that it cannot find an
\code{ffmpeg} executable.

\paragraph{Solution.} Install the \code{video} extra,
\code{pip install ".[video]"}. The \pkg{imageio-ffmpeg} package (version
0.5.1 or newer; older versions fail with recent setuptools) ships its own
\code{ffmpeg} binary, so no system installation is needed.
\code{env-lib run -{}-gif out.mp4} checks for the extra before the rollout.
GIF export uses Pillow, a dependency of the base installation, and is the
fallback when a video codec is unavailable. \code{save\_animation} rejects other suffixes with
a \code{ValueError}; frames must all have the same shape
\code{(H, W, 3)} or \code{(H, W, 4)}.

\section{Vector environments}\label{sec:trouble-vector}

\paragraph{A Sync instead of a native vector environment.}
\code{env\_lib.make\_vec} uses a native batched implementation only for the ids
that register one: the NumPy \envid{KuramotoOscillator-*} ids,
\envid{Consensus-v0}, \envid{Formation-v0}, \envid{PowerGrid-v0} and
\envid{Platoon-v0}. For every other id it returns Gymnasium's
\code{SyncVectorEnv}, which steps one Python environment per copy, so its cost
grows linearly with \code{num\_envs}. \code{env-lib list -{}-native} lists the
native ids, and \code{env\_lib.get\_spec(id).vector\_entry\_point} is \code{None}
for the others; forcing \code{vectorization\_mode="vector\_entry\_point"} for
such an id raises \code{gymnasium.error.Error} (\code{Cannot create vectorized
environment ... because it doesn't have a vector entry point defined}). A
\code{SyncVectorEnv} does not have the methods of the native classes, so that
the call \code{envs.laplacian\_policy()}, for example, raises an
\code{AttributeError}; the controller returned by
\code{env\_lib.baseline\_policy(envs)} works with both kinds of vector
environment.

\paragraph{AJLATT in Sync and Async vector environments.}
\code{SyncVectorEnv} and \code{AsyncVectorEnv} store one scalar reward per copy,
but AJLATT returns per-robot reward arrays. \code{env\_lib.make\_vec} therefore
wraps every copy in \code{TeamReward} (the per-robot rewards stay in
\code{infos["agent\_rewards"]}). If you pass your own \code{wrappers}, include
\code{TeamReward}; otherwise a step fails with \code{ValueError: setting an
array element with a sequence}. \code{gymnasium.make\_vec} does not add the
wrapper.

\paragraph{Where is the last observation of an episode?}
It depends on the autoreset mode (Table~\ref{tab:workflow-autoreset}). With the
default \code{"next\_step"} mode, the observation returned together with
\code{terminated} or \code{truncated} is the last one of the episode; on the
\emph{next} \code{step()} the copy ignores its action, returns reward 0, both
flags \code{False}, the first observation of the new episode and, in
\code{infos}, the rows of its reset info. With \code{"same\_step"} the returned
observation already belongs to the new episode, and the last observation and
info are in \code{infos["final\_obs"]} (an object array with \code{None} for the
copies that did not finish) and \code{infos["final\_info"]}, masked by
\code{infos["\_final\_obs"]} and \code{infos["\_final\_info"]}. With
\code{"disabled"} nothing is reset; reset the finished copies with
\code{envs.reset(options=\{"reset\_mask": terminated | truncated\})}. When
you store transitions for learning, skip the \code{"next\_step"} reset step (its
observation is not a successor of the previous one); \code{env\_lib.evaluate}
does this.

\paragraph{Errors when selecting the autoreset mode.}
Pass the mode as \code{env\_lib.make\_vec(id, n, autoreset\_mode="same\_step")};
this works for native, Sync and Async environments. Passing
\code{vector\_kwargs} to a native environment raises
\code{gymnasium.error.Error} (\code{Custom vector environment can be passed
arguments only through kwargs}), and \code{gymnasium.make\_vec} with Sync or
Async environments accepts only \code{gymnasium.vector.AutoresetMode} members
or their values (\code{"SameStep"}), not \code{"same\_step"}. Gymnasium~1.0 has
no \code{AutoresetMode}, and its Sync and Async environments always use
next-step autoreset.

\paragraph{Copies do not match single environments.}
A native vector environment draws the initial states of all copies from one
generator, so copy $i$ does not reproduce a single environment reset with seed
$s + i$, whereas \code{SyncVectorEnv} seeds copy $i$ with $s + i$. To compare a
copy with a single environment, start both from the same state through the
reset options (Table~\ref{tab:envlib-options}), or use
\code{vectorization\_mode="sync"}.

\paragraph{\code{ResetNeededError} from a partial first reset.}
The first \code{reset()} of a native vector environment must reset every copy;
\code{reset(options=\{"reset\_mask": mask\})} with some entries \code{False}
before that raises \code{ResetNeededError}.

\section{Warnings about unknown reset options}\label{sec:trouble-reset-options}

\paragraph{Symptom.} \code{reset()} prints a \code{UserWarning} such as
\code{ConsensusEnv.reset(): ignoring unknown reset option(s) ['position'];
supported: ['positions', 'velocities']}.

\paragraph{Cause.} Since version 1.1 the environments with reset options
(Kuramoto, Consensus, PowerGrid, Platoon and their vector versions) ignore keys
they do not know, with this warning, instead of raising \code{ValueError}; the
values of known keys are still validated strictly
(Section~\ref{sec:envlib-reset-options}). This lets generic tools pass options
of their own, as PettingZoo's \code{parallel\_api\_test} does.

\paragraph{Solution.} Check the key against the supported ones printed in the
message: a misspelt key, as in the example, means that the option had no effect
and the initial state was sampled as usual. If a tool passes options on
purpose, silence only its keys, for example
\code{warnings.filterwarnings("ignore", message=r".*reset option.*'options'",
category=UserWarning)}. LineMsg, WirelessComm, Pistonball and AJLATT have no
reset options and ignore \code{options} without a warning.

\section{Reproducibility and seeding}\label{sec:trouble-seeding}

The environments are deterministic given their seeds and never use global
random state, but a complete experiment contains several independent sources
of randomness. Seed each of them:

\begin{itemize}
  \item \emph{Environment.} Call \code{env.reset(seed=s)} once at the start of
    a run; later calls to \code{env.reset()} without a seed continue the same
    random stream, so a whole sequence of episodes is reproducible. Resetting
    with the same seed every episode repeats the same initial state.
  \item \emph{Action sampling.} \code{env.action\_space.sample()} uses the
    space's own generator, which \code{reset} does not seed. Call
    \code{env.action\_space.seed(s)}. This also applies to
    \code{record\_episode} without a policy.
  \item \emph{Construction-time randomness.} Some environments draw random
    structure in the constructor, independent of \code{reset}: the
    Erd\H{o}s-R\'enyi graph of \code{ConsensusEnv} (\code{graph\_seed}; with
    the default \code{None} two instances may differ, even in their
    observation size), the random topology of the Kuramoto environments
    (\code{topology\_seed=42}), the PowerGrid network
    (\code{network\_seed=0}) and the Platoon vehicles
    (\code{vehicle\_seed=0}); with \code{network\_seed=None} or
    \code{vehicle\_seed=None} every instance draws fresh entropy. AJLATT
    accepts a default seed in its configuration (\code{seed=...}), used by the
    first \code{reset()} without a seed.
  \item \emph{Vector environments.} \code{envs.reset(seed=s)} makes a batch
    reproducible; the copies of a native vector environment share one
    generator (Section~\ref{sec:trouble-vector}).
  \item \emph{Networks.} Call \code{torch.manual\_seed(s)} before creating
    networks and before training. \code{VariationalEncoder} samples its noise
    from PyTorch's default generator. On GPUs some operations are
    non-deterministic; see the PyTorch documentation on reproducibility
    (\code{torch.use\_deterministic\_algorithms}).
  \item \emph{Tabular tools.} Pass \code{rng=s} to the tables; each table
    owns its generator.
  \item \emph{Your own code.} Use a \code{numpy.random.default\_rng(s)}
    generator instead of the global \code{np.random} functions.
\end{itemize}

Seeded trajectories are reproducible for a fixed version of the package and
its dependencies. Across versions, results can change where bugs were fixed;
Appendix~\ref{app:migration} lists these changes. The AJLATT environment can
reproduce its behaviour before version 1.0 closely with
\code{ci\_solver="slsqp"}.

\section{Performance}\label{sec:trouble-performance}

\begin{itemize}
  \item \emph{Render only when needed.} Rendering a frame costs 3 to 36\,ms,
    which is far more than a simulation step (Table~\ref{tab:examples-bench}).
    Train with \code{render\_mode=None}, and record evaluation episodes
    separately, with \code{render\_every} greater than one for long episodes.
    \code{"human"} mode additionally limits the frame rate, so never train in
    \code{"human"} mode.
  \item \emph{Create environments once.} Construction loads maps, builds
    graphs and allocates buffers; reuse an environment across episodes with
    \code{reset()} instead of creating a new one per episode. The first
    \code{render()} call builds the figure and is slower than later calls.
  \item \emph{Choose the integrator.} For the Kuramoto environments, Euler
    integration is about twice as fast as RK4; use RK4 when accuracy at large
    \code{dt} matters.
  \item \emph{Batch on the GPU.} The PyTorch Kuramoto environment simulates
    \code{n\_agents} systems per step. One batched environment is much
    cheaper than many separate ones, especially on a GPU.
  \item \emph{AJLATT.} Keep the default \code{ci\_solver="newton"}, which is
    several times faster than \code{"slsqp"}; the cost per step grows with the
    number of robots because every robot fuses its neighbours' estimates.
  \item \emph{Small networks on the CPU.} PyTorch uses several threads by
    default. For the small networks typical of these environments, and when
    several training processes share a machine, thread contention can make
    training much slower. \code{marl\_algorithms.train}, \code{train\_preset}
    and \code{compare} already use one thread (\code{threads=1}); elsewhere
    limit the threads with \code{marl\_algorithms.torch\_threads(1)},
    \code{torch.set\_num\_threads(1)} or the environment variable
    \code{OMP\_NUM\_THREADS=1} and compare.
  \item \emph{Simulate batches natively.} For many copies of an environment
    with a native vector implementation, \code{env\_lib.make\_vec} advances
    all of them with one set of array operations; a \code{SyncVectorEnv} steps
    them one by one, and an \code{AsyncVectorEnv} pays inter-process
    communication on every step, which only an expensive step (AJLATT,
    Pistonball) outweighs.
  \item \emph{Choose the batch size by measurement.} The throughput of a
    native vector environment (environment steps per second) grows with the
    number of copies while the fixed cost per call dominates, then levels off
    and can drop once the arrays no longer fit into the CPU caches: for
    PowerGrid with 128 buses, 1024 copies gave a lower throughput than 64
    (Table~\ref{tab:power-grid-throughput}; Platoon behaves similarly,
    Table~\ref{tab:platoon-throughput}). Run
    \code{env-lib bench ID -{}-num-envs B} for a few values of \code{B} with your
    constructor arguments (\code{-{}-kwarg}) and pick the smallest batch near the
    maximum.
  \item \emph{Pin the BLAS threads.} Some kernels of the native vector
    environments use matrix products (the coupling terms of Kuramoto and of
    PowerGrid with small networks), which NumPy passes to its BLAS library;
    depending on the installation, BLAS starts one thread per core. For the
    small matrices of these environments the threads bring little, and when
    several processes share a machine (parallel runs, \code{AsyncVectorEnv}
    workers) they compete for the cores. Start Python with
    \code{OMP\_NUM\_THREADS=1} (for OpenBLAS also
    \code{OPENBLAS\_NUM\_THREADS=1}, for MKL \code{MKL\_NUM\_THREADS=1}) and
    compare with \code{env-lib bench}; pinned threads also make timings more
    reproducible.
  \item \emph{Measure.} \code{env-lib bench} measures the throughput of the
    single, native vector and Sync (and Async) implementations,
    \code{benchmarks/benchmark\_envs.py} (Section~\ref{sec:examples-benchmarks})
    measures step and frame times on your machine, and
    \code{python -m cProfile -s cumtime script.py} shows where time goes in
    your own code.
\end{itemize}

\section{Training with marl\_algorithms}\label{sec:trouble-marl}

\paragraph{\code{ImportError}: ``requires PyTorch''.} The algorithms need
PyTorch, which the base installation does not include (\code{marl-train}
reports ``PyTorch is not installed'' and exits with status 1). Install the extra,
\code{pip install "my-tool-box[torch]"}, or a PyTorch build of your choice
(Section~\ref{sec:install-torch}).

\paragraph{\code{TypeError} when creating an algorithm.} Every method supports
one kind of action (Table~\ref{tab:marl-algorithms}): MADDPG and MATD3 need
continuous actions, IQL, VDN and QMIX discrete ones, while IPPO and MAPPO
accept both. A joint \code{Discrete} action over several agents, such as
LineMsg with its default \code{action\_space\_type}, is not a per-agent action
and is rejected; \code{make\_vector\_env} therefore creates LineMsg with
\code{action\_space\_type="multibinary"}. Pass the same argument when you build
a LineMsg environment yourself.

\paragraph{\code{ValueError}: \code{VectorRunner} needs same-step autoreset.}
The training loops bootstrap from the true last observation of an episode,
which a vector environment only provides in same-step mode. Create the
environment with \code{marl\_algorithms.make\_vector\_env} or pass
\code{autoreset\_mode="same\_step"} to \code{env\_lib.make\_vec}.

\paragraph{\code{marl-train} reports an unknown algorithm, environment or
field.} \code{marl-train} checks its arguments before training and exits with
status 2 and a message on standard error. Algorithm names are those of
\code{marl-train list}, environment ids those of \code{env-lib list}, and the
keys of \code{-{}-set} the fields of the algorithm's configuration class
(Section~\ref{sec:marl-cli}).

\paragraph{Results differ from the published ones.} A run is determined by its
seed, its configuration and the software it runs on: with the same seed and
PyTorch thread count, the same library versions and the same machine,
training repeats exactly. Other PyTorch or BLAS builds, another number of
threads or another processor change the rounding of floating-point sums, and
reinforcement learning amplifies such differences, so the returns in
Section~\ref{sec:marl-results} are reproduced to within the variation between
seeds rather than digit for digit. Compare several seeds before concluding
that a change helps.

\paragraph{Training is slower than the reported times.} The published times
use one PyTorch thread, the default of \code{train}, \code{train\_preset},
\code{compare}, \code{marl-train} and the demonstration script. A direct call
of \code{algo.learn} uses PyTorch's setting; wrap it in
\code{with marl\_algorithms.torch\_threads(1):}. With PyTorch's default
thread count, the small networks of these methods often train more slowly,
especially when several runs share a machine.

\paragraph{The return does not improve.} Start from a preset
(\code{marl-train presets}), which fixes the learning rates, reward scale and
exploration schedule for its environment; the defaults of the configuration
classes are generic. Without a preset, normalise the observations, scale the
rewards so that the team return per step is of order one, and check the
learning curve of \code{TrainingLog.curve} before increasing
\code{total\_steps}. An off-policy method whose budget ends before
\code{warmup\_steps} warns that it takes no gradient step at all.

\paragraph{The agent learns to end episodes early (Kuramoto, AJLATT).} Two
families reward a behaviour other than the intended one, in their default
reward settings, if a learner maximises the return literally. The Kuramoto ids
other than the \code{FreqSync} ones pay the order parameter $r \in [0, 1]$ at
every step (\code{reward\_mode="dense"}) and end the episode with
\code{sync\_bonus} (10) once $r$ exceeds \code{sync\_threshold} (0.99), so an
agent that stays just below the threshold for the whole episode (up to
\code{max\_steps}, 1000) earns far more than one that synchronises. AJLATT
pays negative rewards (\code{reward\_mode="cost"}) and ends the episode at the
first collision, so an agent can avoid further penalties by colliding. The
registered ids keep these defaults for compatibility; \code{env-lib describe}
prints a caution. For training, choose another reward mode: for Kuramoto
\code{reward\_mode="penalty"} (synchronising sooner earns more),
\code{"progress"} or \code{"terminal"}, or \code{terminate\_on\_sync=False}
(Section~\ref{sec:kuramoto-reward}); for AJLATT \code{reward\_mode="bounded"}
or \code{terminate\_on\_collision=False}, which keeps the collision penalties
(Section~\ref{sec:ajlatt-reward}). With \pkg{marl\_algorithms}, pass them as
\code{env\_kwargs}. Evaluate with the metric you care about
(\code{info["synchronized"]}, \code{info["tracking\_cost"]}) rather than the
return alone.

\paragraph{\code{ValueError} when evaluating or loading an algorithm.}
\code{algo.evaluate} and \code{marl-train evaluate} check that the
environment has the number of agents, observation size and action space the
algorithm was trained for, and name the difference if not; a model trained on
a variant (for example \code{n\_buses=32}) is evaluated on the same variant.
Checkpoints record the environment id and keyword arguments of
\code{train} in \code{algo.metadata}, and \code{marl-train evaluate} prints a
note when they differ from the ones given. \code{Algorithm.load} raises
\code{FileNotFoundError} for a missing path and \code{ValueError} for a file
that is not a checkpoint of this package; load only files you trust, since
checkpoints are pickled. \code{device="cuda"} (or \code{"mps"}) without such a
device raises \code{ValueError} when the algorithm is created.

\section{Other common errors}\label{sec:trouble-other}

\begin{description}[leftmargin=0.6cm,style=nextline]
  \item[\code{step()} raises before the first \code{reset()}]
    Every environment, including the native vector environments, requires
    \code{reset()} before the first \code{step()}. Otherwise it raises
    \code{env\_lib.ResetNeededError}, which can be caught either as a
    \code{RuntimeError} or as Gymnasium's \code{ResetNeeded} error.
    Environments created with \code{gymnasium.make} raise Gymnasium's own
    \code{ResetNeeded} from the \code{OrderEnforcing} wrapper.
  \item[An episode is longer or shorter than expected]
    Each environment enforces its own episode limit through a constructor
    argument (\code{max\_steps}, \code{max\_iter}, \code{max\_cycles} or
    \code{max\_episode\_steps}; \code{env\_lib.get\_spec(id).limit\_kwarg}
    names it). Pass it to the constructor, or pass
    \code{max\_episode\_steps} to \code{env\_lib.make} or
    \code{env\_lib.make\_vec}, which set the same argument; giving both with
    different values raises \code{ValueError}. Only \code{gymnasium.make} called
    directly with \code{max\_episode\_steps} (and \code{gymnasium.make\_vec} in
    the Sync or Async mode) adds a second \code{TimeLimit} wrapper, and the
    shorter of the two limits applies; \code{gymnasium.make\_vec} passes the
    argument on to a native vector class, which rejects it with
    \code{TypeError}. In version 1.0, \code{env\_lib.make} behaved like
    \code{gymnasium.make} here, and for AJLATT the value did not reach the
    environment at all (Section~\ref{sec:migration-11}).
  \item[\code{AttributeError} for an environment method]
    \code{gymnasium.make} and \code{env\_lib.make} return a wrapped
    environment. Methods and attributes that only the environment class
    defines are reached through \code{env.unwrapped}; for example, the
    consensus controller is \code{env.unwrapped.laplacian\_policy()}. The
    function \code{env\_lib.baseline\_policy} needs no such access: it accepts
    wrapped, flattened and vectorised environments.
  \item[\code{TypeError} from \code{baseline\_policy}]
    Keyword arguments set the gains of the controller of the environment's
    family; an unknown name raises \code{TypeError} with the list of valid
    names (\code{env-lib baselines} lists the controllers). A wrapper that
    changes the spaces beyond a reshape, or an environment that is not part of
    \pkg{env\_lib}, raises \code{TypeError} as well.
  \item[\code{render()} returns \code{None} with a warning]
    The environment was created without a render mode. Pass
    \code{render\_mode="rgb\_array"} (or \code{"human"}) to the constructor or
    to \code{make}.
  \item[Actions are rejected]
    Actions must match \code{env.action\_space} in shape. Pistonball in
    discrete mode expects one value in $\{0, 1, 2\}$ per piston, not a single
    integer; AJLATT expects an array of shape \code{(num\_robots, 2)}.
    Appendix~\ref{app:migration} describes the changes from earlier versions.
  \item[The \pkg{parakit} window does not open]
    \code{ParameterTuner.tune()} raises \code{ImportError} without Tk and
    \code{RuntimeError} without a display; use the headless API
    (Section~\ref{sec:parakit-gui}).
  \item[Figures look different from the examples]
    \pkg{plotkit} applies its style locally and does not change global
    settings. If other code changed \code{matplotlib.rcParams} (or called
    \code{set\_research\_style} without \code{reset\_style}), the preset is
    applied on top of those settings; call \code{matplotlib.rcdefaults()} to
    start from the matplotlib defaults.
\end{description}
